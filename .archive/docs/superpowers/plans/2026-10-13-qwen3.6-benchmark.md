# Qwen3.6-35B-A3B Benchmark on nv1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Decide with measurements whether Qwen3.6-35B-A3B at a 2-bit quant can replace LFM2.5-8B-A1B as the model `llama-server` serves on nv1 (speed, memory, answer quality and, above all, multi-turn corruption rate under real Hermes traffic).

**Architecture:** No chart change. `llama-server` is paused through git (`replicaCount: 0`, the only pause that survives self-heal). Throwaway pods in the `llm` namespace then borrow nv1's single GPU: one-shot `llama-bench` pods for raw speed, and a `llama-server` pod carrying the production flag set and the label `app: llama-server`, so the existing Service routes Hermes and Honcho to it with no consumer config change. Models live on the existing `llama-server-models` PVC (baseline PSA, no hostPath, no privileged namespace). A revert PR resumes production. Nothing is swapped by this plan; it ends in a decision and a recorded result.

**Tech Stack:** `ghcr.io/mmalyska/llama-cpp-jetson:v0.6.0` (pinned digest, native sm_87, upstream llama.cpp 0.6.0 of 2026-10-05), Unsloth GGUFs from `unsloth/Qwen3.6-35B-A3B-GGUF`, kubectl, talosctl, Python 3 stdlib scripts, ArgoCD app `llm-server`.

**Spec:** none (benchmark, not a feature). Context: the 2026-10-13 feasibility discussion; `docs/src/k8s/nv1-jetson.md` (memory budget, GPU rules); `.claude/memory/reference_nv1_gpu_test_pause.md` (pause procedure); `.plans/TODO.md` (LFM2.5 corruption tracking, #29002); `.archive/docs/superpowers/plans/2026-09-28-llm-model-swap-lfm2.5.md` (the precedent swap plan).

## Global Constraints

- **Never mutate cluster state without explicit user confirmation** (CLAUDE.md hard rule): every `kubectl apply`, `delete`, `annotate`, every merge and every ArgoCD refresh in this plan is preceded by asking the user.
- The pause is **git-only**: `server.replicaCount: 0` in `cluster/apps/ai/llm/server/values.yaml`, marked TEMPORARY. `kubectl scale` and `selfHeal` patches do not stick.
- nv1 has **one** `nvidia.com/gpu`: only one GPU pod at a time. The production `llama-server` pod must be gone before any bench or server pod is applied.
- Pod memory limit stays `13Gi`; a limit above ~13.4 GiB gives no protection (node starves first). Request `9Gi`. Same production flags: `-ngl 99 -fa on -ctk q8_0 -ctv q4_0 -c 131072 -np 2 --jinja -ub 256` (65536 per slot; Hermes refuses < 64,000).
- Qwen arms start at `--cache-ram 512 --ctx-checkpoints 2` (production LFM is 2048/4 and leaves no room at 10 GiB of weights). Raise only if the memory gate shows >= 1.5 GiB of node headroom.
- Image stays the pinned `llama-cpp-jetson:v0.6.0` digest. A newer build is a separate follow-up, not part of this benchmark.
- Downtime is expected: `LlamaServerUnavailable` goes critical after 10 minutes, Hermes aux tasks fall back to the main (cloud) model and Honcho to cloud. Budget **60-90 minutes**; have the revert PR ready before pausing.
- No secrets, no private domain literal, no Claude attribution in any commit or PR body.

## Review Focus

1. **Hybrid-state corruption (llama.cpp#29002 class).** Qwen3.5/3.6 are Gated-DeltaNet hybrids; LFM2.5 measured 29.0% (n=100) under real Hermes traffic. A Qwen result that is fast but corrupts as often is a reject. Task 6 measures it in the same harness as the baseline arm, not against the old 29% figure.
2. **CUDA 13.2 gibberish warning.** Unsloth's Qwen3.6 page says not to use CUDA 13.2 (gibberish output). nv1's driver is 13.2; whether it applies to our build (toolkit version) is unknown. Task 5 runs known-answer prompts first and, on gibberish, retries once with `-ctk bf16 -ctv bf16` as the page suggests before concluding.
3. **Concurrent near-ceiling memory, not a single request.** The 2026-09-28 OOM passed a sequential test. Task 5 uses 2 simultaneous ~45K-token prompts for 5 rounds.
4. **Thinking mode.** Qwen3.6 thinks by default and reasoning eats `max_tokens`. The server default is `enable_thinking:false`; Task 5 also records thinking-on behaviour, because a "conversations and work" main model may want it.
5. **PVC headroom.** 30Gi holds 7.21 + 10.02 + 10.73 = 27.96 GiB. Task 1 checks `df` before each download and stops if < 1 GiB would remain.

## Decision gates (apply to each Qwen arm, all must hold)

| Gate       | Pass                                                                                                                                                           |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fits       | Pod working set <= 12.5 GiB and node `MemAvailable` >= 0.8 GiB at every sample across 5 concurrent rounds; no OOM kill, no cilium-envoy/node-exporter restarts |
| Speed      | `tg128` >= 12 tok/s (llama-bench) and single-stream generation >= 10 tok/s in server mode with 2 slots busy (LFM2.5: 22-26)                                    |
| Quality    | `probe.py quality` >= 19/20 (95%) and no gibberish                                                                                                             |
| Corruption | Real-Hermes-traffic rate <= 10% at n >= 100, **and** lower than the baseline arm measured in this session                                                      |

All pass -> write a follow-up swap plan (same shape as the LFM2.5 swap plan). Fits+quality but fails speed or corruption -> candidate for a chat-only role (Open WebUI), not Hermes aux. Fails fit -> record and stop; the next step is hardware, not a smaller quant.

### Task 6: Corruption rate under real traffic (the deciding measurement)

**Interfaces:**

- Consumes: `qwen-server` pod from Task 5 (label `app: llama-server`, alias `lfm2.5-8b-a1b`, so Hermes needs no config change).

- [ ] **Step 1: Synthetic multi-turn harness (4 concurrent conversations, 6 turns each, ~7K-token system prompts)**

```bash

```

Expected: a final `CORRUPTION bad/turns = x%` line. `looks_corrupt` flags leaked `<think>` markers, `finish_reason=length` and replies not ending in sentence punctuation (the #29002 failure shape). The baseline arm for comparison is LFM2.5 started with `__EXTRA_ARGS__` = `--chat-template-kwargs '{}' --reasoning-budget 64 --cache-ram 2048 --ctx-checkpoints 4` (production values).

- [ ] **Step 2: Real Hermes traffic through the Service**

```bash
kubectl -n hermes-agent exec deploy/hermes-agent -c hermes-agent -- ls /opt/data/profiles
```

For each of 4 profiles run, concurrently, `hermes -p <profile> chat -q "<varied task prompt that needs a tool call>"` in a loop of 25 rounds, saving every reply to a file and counting replies that contain `<think>`, are empty, or end without terminal punctuation:

```bash
for p in <p1> <p2> <p3> <p4>; do
  ( for i in $(seq 1 25); do
      kubectl -n hermes-agent exec deploy/hermes-agent -c hermes-agent -- \
        hermes -p "$p" chat -q "List the three most important checks before upgrading a Kubernetes node, then call a tool if you have one." \
        > "/tmp/qwen-h-$p-$i.txt" 2>&1
    done ) &
done; wait
grep -lE "<think>|</think>" /tmp/qwen-h-*.txt | wc -l
find /tmp -name 'qwen-h-*.txt' -size -20c | wc -l
```

Expected: 100 reply files; corrupt = leaked-think + empty + truncated. Compare Qwen arm vs baseline arm. This is the method the 29.0% figure came from (4 profiles, real tool calls, real system-prompt-sized context).
