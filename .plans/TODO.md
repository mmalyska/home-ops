Not just `UnattendedInstallConfig.provisioning.diskSelector.match`: any `cel.Expression`, `block.ByteSize` or `block.PercentageSize` value in the base document is replaced by the patch's zero value (also `VolumeConfig`/`UserVolumeConfig` `diskSelector.match` and `minSize`, `OOMConfig` `triggerExpression`, `LinkAliasConfig` `selector.match`); plain fields, `maxSize`, `ResolverConfig` addresses and `WatchdogTimerConfig` `timeout` are kept. `gen config --config-patch` is affected too; `talosctl patch mc` is untested (needs a node). A zero guard in those three methods fixed it in a local copy; offer it as a comment or PR if a maintainer asks. Our workaround stays until a fixed release: the selector is repeated in the last patch per node (`controlplane/05`, `worker/05`, `node/nv1/20`), guarded by `tests/test_render.sh`. Remaining here: check the issue after each new Talos release and drop the repeated selectors once fixed (re-run `task talos:check`). ## AI — Hermes

- [ ] **vLLM for LFM2.5-8B-A1B on nv1 — was blocked on JetPack 7 (CUDA 13); the CUDA 13 driver is on nv1 now, a CUDA 13 build for sm_87 is what is left.**
  **Update 2026-10-10:** nv1 runs the JetPack 7 stack (CUDA 13.2 driver libraries, `cuInit` works, llama.cpp on the GPU), so the gate in the conclusion below is gone. What remains is build engineering: a vLLM >= 0.23 (needs `RoutedExperts`, PyTorch 2.11, `[cu13]` extras) built for aarch64/Orin sm_87 against CUDA 13.2, in a container that mounts the r39 libraries via the CDI spec (`/usr/local/lib/nvidia-tegra`). Memory is the other constraint (about 1.7 GB free with the current llama-server; see `docs/src/k8s/nv1-jetson.md`).
  Original investigation 2026-10-01 whether a different inference engine could sidestep llama.cpp's hybrid-state corruption bug (see the corruption-rate entry below) for the main model. LFM2.5 has official vLLM support, and NVIDIA publishes `ghcr.io/nvidia-ai-iot/vllm:latest-jetson-orin` (vLLM 0.19.0) for exactly this hardware (JetPack6/r36.4/CUDA12.6/Orin sm_87) — but hit a chain of real blockers trying to actually load our model:
  1. GGUF repo has no `config.json` (fixable: `--hf-config-path`).
  2. `LiquidAI/LFM2.5-8B-A1B`'s tokenizer config uses a Transformers 5.2+ convention (`tokenizer_class: TokenizersBackend`) this image's bundled Transformers 4.57.3 doesn't recognize (fixable: patch `tokenizer_config.json` to `PreTrainedTokenizerFast`, verified working).
  3. vLLM's **in-tree GGUF loader** hard-fails: `RuntimeError: Unknown gguf model_type: lfm2_moe` — a hardcoded architecture allowlist that doesn't include LFM2's MoE variant yet (same recurring gap previously hit by Mixtral, Qwen3.5, Gemma3, Qwen3-MoE — each needed a small mapping fix added upstream; none exists yet for `lfm2_moe`).
  4. Tried the newer, actively-developed out-of-tree `vllm-gguf-plugin` (generic tensor-name adapter, architecturally different from the in-tree allowlist) instead: it requires `huggingface_hub>=1.26.0`, which conflicts with this image's `transformers==4.57.3` (hard runtime-enforced pin to `<1.0`, not just declared metadata — confirmed by patching the enforcement check directly and verifying transformers/tokenizers still function correctly at 1.26.0). Even past that, the plugin needs vLLM's `RoutedExperts` API (`vllm.model_executor.layers.fused_moe`), **confirmed absent from vLLM 0.19.0 entirely** (grepped the installed package directly — only an older, differently-shaped `routed_experts_capturer.py` exists).
  5.   6. Checked for an existing community build recipe at this version for Jetson **Orin** specifically: none exists. - [ ] **Re-check llama.cpp's hybrid/recurrent-state bugs periodically — revisit the LFM2.5 corruption-rate acceptance if fixed.** nv1's `llama-server` runs LFM2.5-8B-A1B as both the main model and aux tasks/compression despite a known, unfixed upstream bug in llama.cpp's handling of hybrid (recurrent/short-conv) model state under multi-sequence serving: [ggml-org/llama.cpp#29002](https://github.com/ggml-org/llama.cpp/issues/29002) (LFM2/LFM2.5, co-batching corrupts recurrent state, reproduced down to the 350M size, open as of 2026-09-16 master), plus the same bug class independently in other hybrid architectures — [#27442](https://github.com/ggml-org/llama.cpp/issues/27442) (Qwen3.5-MoE, empty generation past ~16K tokens), [#22384](https://github.com/ggml-org/llama.cpp/issues/22384) (generic checkpoint-restore for hybrid/recurrent models), [ollama#18528](https://github.com/ollama/ollama/issues/18528) (Qwen3.5/3.6 GDN hybrids, cross-request state leak on ROCm). A generic fix was still in progress as of PR [#29426](https://github.com/ggml-org/llama.cpp/pull/29426) (test refactor, not yet a fix). - [ ] **Follow-up: extend nv1 `llama-server`'s concurrency (`-np`), per-slot context, and/or `ctxCheckpoints` further, now that real headroom is confirmed.** PR #5349 (merged 2026-09-30) shipped LFM2.5-8B-A1B at `-np 2 -c 131072` (65536 tokens/slot, Hermes' hard floor) with `ctxCheckpoints: 4`. That's roughly **6 GiB of unused, real headroom**, confirmed empirically (not estimated), on top of `ctxCheckpoints` already having been bumped 2→4 within this budget. Two independent levers are worth spending it on, and they compose (raising one doesn't rule out the other):
  - **A 3rd parallel slot.** Cannot just add `-np 3` at the current `-c 131072` — that drops per-slot context to ~43690, below Hermes' hard 64,000-token floor (`agent_init._enforce_minimum_context`). Needs `-c` raised to at least `3 × 65536 = 196608` to keep 3 full-sized slots, which also grows the KV-cache/checkpoint budget per slot — re-measure, don't assume it scales linearly from the 2-slot number above.
  - **Larger per-slot context** (e.g. `-c 196608 -np 2` → 98304/slot) instead of more slots — more headroom per conversation (Hermes/Honcho calls that exceed 64K today get truncated/rejected), no change to `agent_init`'s floor math, but also grows KV-cache size per slot.

Don't reason from KV-cache math alone (LFM2.5's hybrid recurrent/short-conv architecture makes per-token KV growth much cheaper than a standard transformer, so naive per-token estimates from a dense-model mental model will be wrong) — measure, like Task 3 did.

## Storage — Rook-Ceph

- [ ] **🔒 GATED — Migrate CSI keys to the `aes256k` cipher and unmute the CephX warnings** — do **not** start until *both* gates below are true. Full background: `docs/src/k8s/rook-ceph-cephx.md`.
  - **Gate 1 — Linux kernel 7.0+ on every node.** `aes256k` is used by the *kernel* RBD/CephFS clients; forcing it on a 6.x kernel breaks every kernel mount and takes out all PVCs. Talos tracks the 6.18 **longterm** branch, so this is blocked on Talos adopting a 7.x kernel, not on Linux releasing one (7.2.x was already stable in 2026-09 while Talos v1.15 alphas were still on 6.18.49). Check: `kubectl get nodes -o custom-columns='NAME:.metadata.name,KERNEL:.status.nodeInfo.kernelVersion'`
  - **Gate 2 — ceph-csi ≥ v3.17.1** (was v3.17.0 at time of writing; Renovate will close this on its own). Check: `kubectl -n rook-ceph get pods -o jsonpath='{range .items[*]}{range .spec.containers[*]}{.image}{"\n"}{end}{end}' | grep cephcsi | sort -u`
  - **Then**, following Rook's "Migrating CSI keys to a new key type": rotate CSI keys with `keyType: aes256k`, `keyRotationPolicy: KeyGeneration`, a bumped `keyGeneration`, and `keepPriorKeyCountMax: 1` so in-use keys stay active; wait for `status.cephx.csi.keyGeneration`; then cordon/drain/reboot/uncordon each node in turn so pods remount with the new keys; then `keepPriorKeyCountMax: 0`.
  - **Finally**, restrict `spec.security.cephx.allowedCiphers` to `aes256k` and flip all four `spec.healthCheck.muteHealthWarning` entries in `cluster/apps/core/rook-ceph/cluster/values.yaml` from `mute` to `unmute`, so any stray `aes` key becomes visible again. Leaving them muted after migration is the failure mode to avoid — it would hide a real regression.
  - Do **not** set `allowedCiphers` before the CSI keys have moved: the CRD warns it "can disrupt cluster availability", and restricting it early locks out the CSI clients — an immediate storage outage.
