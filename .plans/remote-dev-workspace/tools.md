## Findings

- **F1. The Taskfile uses sudo, but already skips installation when the right version is present.** `task talos:install` (`install:talos`, `.taskfiles/talos/Taskfile.yaml`) and `task cilium:install` (`install:cli`, `.taskfiles/cilium.yml`) both carry a `status:` check on the installed version (`talosctl version --client --short` matches `TALOS_VERSION`; `cilium version --client` matches `CILIUM_VERSION`). If the image preinstalls a tool at the pinned version, Task considers the target up to date and the `sudo rm`, `sudo tar` and the `talos.dev/install` pipe are never reached. They are reached when the tool is missing or the version differs, and in the workspace (no sudo, D13) that fails. T17 should therefore cover: what happens on a version mismatch (fail with a clear message, or install into a non-root path, instead of calling sudo), and the Homebrew-dependent initialization: `task init` requires `brew` and the Brewfile under `.github/.devcontainer/` (deleted by T10), and `onCreateCommand.sh` calls `chezmoi` through the Homebrew path. T2 only has to make the preinstalled versions equal to `TALOS_VERSION` and `CILIUM_VERSION`.
- **F2. Two talosctl versions are in use.** `home-ops` pins `v1.14.4` in `.taskfiles/talos/Taskfile.yaml` (and `task talos:generate` requires an exact match with `TALOS_VERSION`), while `sandbox-devops` pins `v1.14.5`. The image should carry the home-ops pin; Renovate bumps both with the node upgrade. (Also noted in `talos-access.md`.)
- **F3. Two tools the repository calls are not in the Brewfile.** `shellcheck` (LOCAL_CHECK in `permissions.md`, run in CI over `.agents/bin` and `.agents/tests`) and `markdownlint` (`task lint:markdown`) are missing from `.github/.devcontainer/local-features/common/Brewfile`; `bws`, `coder`, `codex`, `claude`, `krew`, `cilium` and `talosctl` come from other places. The list in the plan task (Brewfile only) is therefore not the whole set. CI does not shellcheck `.envrc` (MegaLinter lists `BASH_SHELLCHECK` as skipped), so the image should carry `shellcheck` for local checks.
- **F4. The `coder` CLI and the server differ in version.** The CLI pin in the `coder-cli` feature is `v2.38.0` (published 2026-10-06, not a prerelease), the server chart in `cluster/apps/ai/coder` is `2.34.0`. The GitHub "latest" release endpoint returned `v2.37.9` on the day of the inventory; that selection says nothing about whether a higher version exists, and no explanation for it is offered here. Check client/server compatibility in T7; nothing was verified here.
- **F5. `containers` needs Docker for `task test`.** `dgoss` runs the image under Docker; Docker is a non-goal for the workspace, so image tests stay in GitHub Actions and the workspace only needs `cue`, `task`, `gh` and `goss` for static checks.
- **F6. `argocd-secret-replacer` targets .NET 10.** `Directory.Build.props` sets `net10.0` and its devcontainer image is `dotnet:10.0`, but its `CLAUDE.md` still says .NET 9. Not an image concern, but the SDK pin must follow the code, not the doc.
- **F7. Paths under `/home/vscode` to avoid or seed (D34).** `~/.krew`, npm global installs, pip user installs, `~/.claude`, `~/.config/chezmoi`, shell rc hook lines. The `.profile` and rc lines appended by feature scripts must move into seed files, or into system-wide files such as `/etc/profile.d/`.
- **F8. Brew-managed tools have no version pin today.** `brew bundle upgrade` runs at build time and on every `task init`, so the versions in section 1 and 3 with "none" are whatever Homebrew had at build time. The new image fixes this by pinning each one; first pins can be read from the current devcontainer (`<tool> --version`) in T2, but that was not done here (nothing was run).
