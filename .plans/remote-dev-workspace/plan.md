# Always-on development workspace on the cluster

## Goal

One persistent, always-on development environment on the Talos cluster (Coder), in which the owner can work on `home-ops` and on other repositories of their account (`containers`, `claude-plugins`, `argocd-secret-replacer` and others). It is an evolution of the local devcontainer, not a replacement: the local devcontainer stays and keeps working.

A single shared base image, built in `containers`, feeds both the Coder workspace and the devcontainers of this and other repositories. Secrets for a workspace come from a dedicated Bitwarden Secrets Manager (BWS) project per workspace type, read with a token scoped to that project only. Cluster access is not a BWS secret: it comes from the Talos and Kubernetes service-account mechanisms, granted per workspace.

## Non-goals

- Replacing or changing the `devops` Coder workspace and the `sandbox-*` images. Hermes uses them (`hermes-agent` SSHes into `sandbox-devops`); see Decisions.
- Running Docker, `docker build` or compose inside the workspace. Images are built in GitHub Actions.
- Public (internet) access to Coder. It stays on `envoy-internal` (LAN and VPN).
- Retiring the local devcontainer.

## Current state (facts, verified 2026-11-02)

See [evidence.md](evidence.md). In short:

- `home-ops-devcontainer` is built in this repo from `.github/.devcontainer` with `devcontainers/ci` (amd64 and arm64). Tools come from local features: homebrew, common, bws-cli, coder-cli, codex-cli, plus Go. Repo setup is in `.devcontainer/scripts/*.sh`.
- `sandbox-{base,devops,dotnet,node,python}` are plain Dockerfiles in `containers/apps/`, amd64 only, user `coder`, sshd and passwordless sudo. They contain none of: Claude Code, `bws`, `gh`, direnv, task, pre-commit, chezmoi, Homebrew, Go.
- The Coder template (`cluster/apps/ai/coder/workspace-template/main.tf`) runs one Deployment per workspace as root, with sshd started from `startup_script`, a fixed LoadBalancer IP for SSH, a ceph-block home PVC (default parameter 2Gi) and a VolSync restic backup of the whole PVC every 6 hours. Limits are 1 CPU and 2 Gi.
- The Coder HTTPRoute is on `envoy-internal` only. The namespace enforces Pod Security `baseline`.
- Baseline from the local devcontainer (one repo, one Claude session): memory 1.6 GiB in use, 2.1 GiB peak; `/workspaces` 2.8 GB, home 1.8 GB.

## Design

### 1. Image (in `containers`)

- New app, working name `dev-workstation`, next to `sandbox-*`, following the same layout (`Dockerfile`, `metadata.json`, `ci/`, `README.md`) and the same Renovate annotations.
- Base: pinned Ubuntu LTS digest, like the current devcontainer image. Non-root user with UID 1000.
- Every tool is installed under a system path, never under `/home/vscode`, because a volume is mounted over the home directory (D34).
- Contents are the union of: the devcontainer features (common, bws-cli, coder-cli, codex-cli, Go; Homebrew is not carried over, D12), the `sandbox-devops` tools (kubectl, helm, talosctl, terraform, k9s, age) and what the repo scripts call (gh, direnv, task, pre-commit, chezmoi, krew, an SSH client with `ssh-agent`). Claude Code is added. `talosctl` is pinned to the `TALOS_VERSION` of this repository (see T2). Exact list comes from task T1.
- Every tool download resolves the architecture (no hard-coded `amd64`) and is version-pinned with a Renovate annotation and a checksum where upstream publishes one.
- One image, two uses. The image carries the `devcontainer.metadata` label so a repository's `devcontainer.json` can reference it with `"image": ...` and no `features` block, and Coder can run it with the agent init script as the command. There is no second tag (D19).
- Published multi-arch to GHCR by the `containers` pipeline, which first gets native per-platform builds, per-platform Goss tests and a merged manifest (D33, task T15). Consumers reference the image by digest, kept current by Renovate, as `.devcontainer/devcontainer.json` does today.

### 2. Coder template and workspace

- A new template (working name `dev`) so the Hermes-facing `sandbox` template is not touched (D16).
- One workspace, one persistent volume `dev-workspace-data` (20 Gi, owned by GitOps, D39) mounted twice with `subPath`: `home` at `/home/vscode` and `workspaces` at `/workspaces` (D14, D34). Repositories live under `/workspaces/<repo>`, which keeps every path assumed by existing scripts and every Claude project directory key identical to the local devcontainer. The image's own home is hidden by the mount, so a first-start step seeds an empty home from seed files and fixes ownership; logins, dotfiles and tool state then persist and are backed up.
- Pod runs as the non-root `vscode` user, no sudo, no privilege escalation, all capabilities dropped (D13, D17). The existing `baseline` Pod Security level is satisfied.
- SSH goes through Coder's built-in agent tunnel (`coder config-ssh` writes the VS Code Remote-SSH host entry), which removes sshd, the root requirement, the per-workspace LoadBalancer IP and the `authorized_key` parameter (D15).
- Resources: requests equal limits for memory (3 Gi), CPU limit 2, CPU request chosen from the measurement in T9. The PVC is not a template parameter: its size (20 Gi, D18) is set in the GitOps manifest (D39); the current template default of 2Gi is too small (the local baseline is about 4.6 GB before any build cache).
- The pod runs in its own namespace `dev-workspace` (D28), has an ingress deny-all NetworkPolicy (D22), and takes its secret reference as a parameter (D11).
- Backups: a `ReplicationSource` and its restic `ExternalSecret` are owned by GitOps in `dev-workspace`, not created by the provisioner (D35), and cover both subPaths (D34). See Risks R2 and R8.

### 3. Secrets (BWS)

- One BWS project per workspace type holds what that type needs; one machine-account token per project, read-only. The dev workspace's project holds `GITHUB_TOKEN`, `TERRAFORM_TOKEN`, the SSH signing key (D32), and the ArgoCD account token and server address (D29). The template takes the name of the `ExternalSecret`/Secret as a parameter so a Hermes sandbox type can use a smaller project later. The owner creates projects and tokens; nothing in this repository names a project or its identifiers.
- Note: the local flow loads an existing BWS project wholesale (`.envrc`: `bws secret list <project> -o env`). The local `task talos:init` builds the talosconfig from the `TALHELPER_*` Talos secrets in that project. The workspace will not receive those secrets, so `task talos:init` cannot run there (also because `task talos:install` uses `sudo`); see section 3a.
- Delivery: an `ExternalSecret` (store `bitwarden`), owned by GitOps in `dev-workspace` (D35), creates a Kubernetes Secret holding the machine token and the project reference. The pod receives them through `secret_key_ref`, the same pattern as `LITELLM_API_KEY`. No secret value passes through Terraform variables, so none reaches Terraform state.
- At workspace start an entrypoint step runs the BWS CLI once and exports the project's secrets to the shell environment of the session (equivalent to `bws run`), failing soft with a clear message when the token is missing.
- The dedicated SSH signing key (D32) is stored in BWS as a secret value. At start it is written to a memory-backed `emptyDir` with mode 0600 and loaded into an in-pod `ssh-agent`; the workspace's git configuration points `user.signingkey` at it (the dotfiles hard-code the owner's own signing key, so a workspace-only override is needed, task T16). It never reaches the home volume and is re-created on every start. The owner registers the matching public key on GitHub as a signing key.
- Secret inventory for the dev workspace (names only): `GITHUB_TOKEN`, `TERRAFORM_TOKEN`, SSH signing key (D32), the ArgoCD account token and server address (D29), plus `BWS_ACCESS_TOKEN` itself, which is the scoped machine token delivered by the Kubernetes Secret and exported into the session so the `bws` CLI works (it is not stored in BWS). `SOPS_AGE_KEY` is deprecated and not part of the workspace (D30). `BWS_PROJECT_ID` also comes from the Kubernetes Secret, so `.envrc` loads the workspace's own project (D31).

### 3a. Cluster access (not BWS)

- Talos: the control planes already run `KubeTalosAPIAccessConfig` (`provision/talos/patches/controlplane/40-talos-api-access.yaml`; roles `os:etcd:backup` and `os:admin`; namespaces `talos-backup` and `tuppr`) and the `serviceaccounts.talos.dev` CRD is installed. The workspace gets a `talos.dev/v1alpha1` `ServiceAccount` with `roles: [os:reader]`; Talos generates a Secret containing a talosconfig, mounted into the pod (field and mount details: `talosctl inject serviceaccount` output in the [Talos guide](https://docs.siderolabs.com/kubernetes-guides/advanced-guides/talos-api-access-from-k8s)). This needs `os:reader` added to `allowedRoles` and the workspace namespace added to `allowedKubernetesNamespaces`: a control-plane machine config change (consent-gated `apply-config`).
- Escalation risk: `allowedRoles` is cluster-wide and already contains `os:admin`. Anyone who can create a `ServiceAccount.talos.dev` in an allowed namespace can request `os:admin`. The workspace therefore needs its own namespace (D28), and RBAC must stop everything except GitOps from creating those resources there. The Coder provisioner has broad RBAC in `coder`, so the workspace must not be provisioned into `coder` with that namespace allowed.
- Spike T12 answered what the docs leave out (details and sources in [talos-access.md](talos-access.md), read from the Talos v1.14.4 source): the Secret has one key `config` (a talosconfig with endpoint `talos.default`, no nodes list); its client certificate lives 6 hours and is renewed by the controller when under 1 hour remains; a resource needs both an allowed namespace and every role in `allowedRoles`; `os:reader` cannot run `talosctl kubeconfig`, read files or change anything; revocation means deleting the resource and waiting up to 6 hours. Still unverified: pod-to-`talos.default` reachability from the new namespace and which `talosctl get` types are sensitive (checked live in T7).
- Kubernetes (D26, D27): a Kubernetes ServiceAccount in `dev-workspace` bound to read-only roles written as explicit lists. RBAC has no exclusion rules, and a wildcard resource also matches subresources such as `nodes/proxy`, `pods/exec` and `serviceaccounts/token`, so "everything except Secrets" is not a safe rule and no rule uses `resources: ["*"]` on the core or built-in groups. Design: (1) bind the built-in `view` ClusterRole, which excludes Secrets and has no proxy, exec or token subresources; (2) add one reviewed ClusterRole with `get`, `list` and `watch` on a short list of cluster-scoped resources (nodes, namespaces, persistentvolumes, storageclasses, customresourcedefinitions and the `metrics.k8s.io` pod and node resources) and on the named resources of each CRD group the owner uses (for example ArgoCD, CNPG, Cilium, Gateway API and Envoy Gateway, External Secrets, VolSync, Rook and Ceph, Prometheus Operator, cert-manager), derived from the live CRDs in T19, with each group justified and each resource type reviewed for credential-bearing fields; (3) nothing else. Authorization is verified in two ways, never by attempting a forbidden read. First, the effective rules are reviewed, not only the source: the aggregated `view` ClusterRole and the output of `kubectl auth can-i --list` for the ServiceAccount. Second, concrete `kubectl auth can-i` checks must answer `no`: `get`, `list`, `watch` on `secrets`; `get` on `nodes/proxy`, `pods/proxy`, `services/proxy`; `get` and `create` on `pods/exec`, `pods/attach`, `pods/portforward` (exec can run over a GET); `update` and `patch` on `pods/ephemeralcontainers`; `create` on `serviceaccounts/token`; `get` on `certificatesigningrequests`; `impersonate`, `escalate`, `bind`; and `create`, `update`, `patch`, `delete` on each concrete resource that matters (pods, deployments, configmaps, services, namespaces, roles, rolebindings, clusterroles, clusterrolebindings, serviceaccounts, customresourcedefinitions, `externalsecrets`, `serviceaccounts.talos.dev`). A check on `*` alone is not evidence: it matches only rules that name `*`, so it can answer `no` while individual resources are writable. A positive control answers `yes` for the intended reads. Nothing is stored or regenerated; the pod uses the projected, auto-rotating ServiceAccount token, so `KUBECONFIG` is not needed.
- ArgoCD (D29): a dedicated ArgoCD local account (API key only, no password login) with its token delivered as an environment variable, together with the server address (it contains the private domain). SSO is not used: `cluster/apps/core/argocd/patches/argocd-rbac-cm.yaml` maps the owner's identity and the `ArgoCDAdmins` group to `role:admin`, so an SSO session in the workspace would give a compromised workspace admin rights over every app and bypass the read-only Kubernetes design. The account may read, refresh, sync and prune, as the owner asked; that is a mutation capability held by the workspace, so its scope is limited by D38 and R9 applies. A token that can sync does not replace consent: `ArgoCD sync` is RUNTIME_MUTATION in `AGENTS.md` and needs fresh consent for each action. Revision protection: without it a sync can select an arbitrary revision, such as an unmerged branch or an older commit, so `application.sync.requireOverridePrivilegeForRevisionSync` is set to `"true"` in `argocd-cm` (documented since ArgoCD v3.2; v3.5.6 is deployed) and the `override` action is never granted. Scope is the named allowlist of D38. Config change: task T18.
- `.envrc` exports `KUBECONFIG` as `~/.kube/config` and defaults `TALOSCONFIG` to a file inside the repository tree (`${TALOSCONFIG:-...}`). In the workspace the pod environment sets `TALOSCONFIG` to the mounted Secret, which wins over the default. No kubeconfig file is created, so kubectl must fall back to the in-cluster configuration; T7 verifies this and, if the `KUBECONFIG` export gets in the way, the `.envrc` change (T14) handles it. No credential file may land on the backed-up volume.

### 4. Repositories and bootstrap

- A list of repositories to clone (public repo names, no secrets) is kept in `mmalyska/dotfiles` and applied by chezmoi on bootstrap (D21).
- A bootstrap step in the image applies the chezmoi dotfiles non-interactively (which, with the workspace flag set, set git identity and SSH signing and clone the listed repositories, task T16) and then runs each repository's own setup. Because `devcontainer.json` lifecycle commands only run under a devcontainer tool, the bootstrap either calls the three scripts a repository names (`onCreateCommand`, `updateContentCommand`, `postStartCommand`) directly or each repository gains a small tool-agnostic `setup` entry point that `devcontainer.json` also calls. T6 is a spike that picks one.
- The worktree rule from `AGENTS.md` applies unchanged: primary checkouts stay on `main`; work happens in `.worktrees/`.
- Claude memory symlinks (`postStartCommand.sh`) are generalised from the hard-coded home-ops path to the current repository, so they keep working under `/workspaces/<repo>`.

### 5. Migration of other devcontainers

After the image is stable, `home-ops` switches `.devcontainer/devcontainer.json` from `home-ops-devcontainer` to the new image and deletes `.github/.devcontainer`, its publish workflow and its Renovate rules. `containers`, `claude-plugins` and the other repositories follow one at a time. Each switch is its own PR and keeps the previous image digest as the rollback. The bootstrap rework (T17, D36) comes first: deleting `.github/.devcontainer/` also deletes the Brewfile that `task init` reads, and `onCreateCommand.sh` calls `chezmoi` through its Homebrew path.

| R1  | The SSH signing key, the BWS token and cluster credentials live in a pod on the cluster they administer. With `os:reader` a compromised workspace cannot change Talos, and its Kubernetes ServiceAccount is read-only without Secrets (D27).
