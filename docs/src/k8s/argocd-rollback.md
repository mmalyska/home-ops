# Rolling back an ArgoCD application

Argo CD refuses a rollback while auto-sync is on
("Rollback cannot be performed against an application with automated sync enabled").
Our Applications are generated by ApplicationSets, and the ApplicationSet controller resets any hand edit
of an Application to the template, so turning auto-sync off in the UI is reverted within seconds.
UI rollback is therefore not available, by design.

## Procedure

Roll back through git:

1. Revert the bad commit (`git revert <sha>`) on a branch and open a PR.
2. Merge it. Auto-sync applies the reverted state.

To stop an app from syncing while a fix is prepared, set `syncPolicy.enabled: false` in its `app-config.yaml`
and merge that; set it back to `true` with the fix.

## Rejected: `ignoreApplicationDifferences` on the auto-sync switch

An ApplicationSet can tell its controller to leave a field alone:

```yaml
spec:
  ignoreApplicationDifferences:
    - jsonPointers:
        - /spec/syncPolicy/automated/enabled
```

It works on Argo CD v3.6.1. It was tested on 2026-11-13 with a throwaway ApplicationSet and as a trial on
bookorbit (#6264): a hand toggle survived ApplicationSet reconciles, the app stayed `Synced`/`Healthy`,
and `argocd_app_info` reported `autosync_enabled="false"`.

It was removed because the ignored field stops following git in both directions: once the Application
exists, a change of `syncPolicy.enabled` in `app-config.yaml` never reaches it. The live state can then
differ from git, and the cluster must not diverge from git.

## Watch upstream

Argo CD PR [#29926](https://github.com/argoproj/argo-cd/pull/29926) (issue
[#9570](https://github.com/argoproj/argo-cd/issues/9570)) would allow a rollback with auto-sync on, switched on
in `argocd-cm`, which is in git. If it ships, it gives UI rollback without the drift above.
