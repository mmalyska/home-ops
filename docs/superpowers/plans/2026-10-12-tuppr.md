# tuppr Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Install tuppr so a merged Renovate bump rolls Talos and Kubernetes upgrades out to mc1, mc2, mc3 and nv1, one node at a time, behind a Ceph / CNPG / backup health gate, with the first rollout gated by a `suspend` annotation in git.

**Architecture:** An ArgoCD app `cluster/apps/system/tuppr` wraps the upstream `tuppr` OCI chart and ships one `TalosUpgrade` and one `KubernetesUpgrade` as templates. The controller reaches the Talos API through `KubeTalosAPIAccessConfig` (control planes). nv1 is upgraded like any node because its installer image also carries a plain `v<talos>` tag.

**Tech Stack:** tuppr chart 0.5.7 (`oci://ghcr.io/home-operations/charts`), Helm, ArgoCD, Talos 1.14 config documents (`provision/talos/patches`), Renovate regex managers, CEL health checks.

**Spec:** `docs/superpowers/specs/2026-10-12-tuppr-design.md`

**Status (2026-10-12): implemented, real-upgrade verification pending.** The controller, access document, alias tags,
both upgrade plans and the alerts are in place and merged (PRs #5644, #5648, #5649, #5651, #5652). The first run was a
verified no-op (see "The first run" in `docs/src/k8s/tuppr.md`). Open: Task 8 Steps 4 and 5 (the first real patch bump:
health gate, pre-pull, drain, nv1 image swap, then `task talos:diff` clean) and Task 11 Steps 1 to 3. Deviations from
the text below: nv1 uses the per-line repository `custom-installer-jp7` (Tasks 1 and 3, see the fork branch
`pr/jetpack7-r39`), the one-off maintenance window used for the first run is already removed again, and Task 11 was
done before a clean real Talos run, at the owner's call.

## Global Constraints

- Namespace `tuppr`; app dir `cluster/apps/system/tuppr`; `syncPolicy.enabled: true`, `selfHeal: true`, `prune: false`.
- `KubernetesUpgrade` allows exactly one resource (`kubernetes`); `TalosUpgrade` is `cluster`, no `nodeSelector`, `parallelism: 1`.
- Both CRs carry `tuppr.home-operations.com/suspend: "true"` until Task 8.
- No pre-hooks (they suppress inter-batch health checks). Ceph `noout` is not handled by tuppr.
- Never commit secret values (gitleaks). Never write the private domain literally.
- Never mutate cluster state (merge that syncs, `kubectl apply/annotate/delete`, `talosctl apply`, reboot) without explicit user confirmation. Steps marked **[CONFIRM]** need it.
- Branch `feat/tuppr` (worktree `.worktrees/feat/tuppr`); push and open a PR after each commit batch; no Claude attribution in commits or PR bodies.
- Existing tests: `provision/talos/tests/run.sh`; lint: `task lint:all`.

## Execution order

Tasks run in this order: 0 to 5, then **7 before 6**, then 8 to 11. Task 7 (the Talos API access document, applied live
from the branch checkout) must be live before the PR of Task 6 is merged: the controller mounts Secret `tuppr-talosconfig`,
which Talos creates only once the document allows `tuppr` / `os:admin`, and the webhook has `failurePolicy: Fail`. The
chart `PrometheusRule` is off (`prometheusRule.enabled: false` in `values.yaml`) until Task 11, because `TupprUpgradeBlocked`
fires for every suspended CR.

## Review Focus

- **`os:admin` is shared with `talos-backup`.** `KubeTalosAPIAccessConfig` has one `allowedRoles` list and one `allowedKubernetesNamespaces` list, so `talos-backup` gains `os:admin` too. Task 2 records this and the user must accept it (spec said "tuppr only").
- **A Job in any namespace holds the run.** A stuck or long-running Job blocks every upgrade (fail closed). Task 5 lists today's active Jobs; the check is narrowed only if it blocks too often.
- **A node reporting a different version than the target.** nv1 compares the version it reports with `v<talos>`; a stale UKI (Jetson UEFI) fails the verification. The existing runbook applies (Task 9 links it).
- **Alias tag missing or moved.** If `custom-installer-jp7:v<talos>` does not exist the run parks as `WaitingForImage`; if it points at a different build than expected nv1 gets the wrong kernel. Task 1 verifies the digests match.
- **Drift after a run.** tuppr patches the live install image; if the repo renders a different image `task talos:diff` stays dirty. Task 3 makes nv1 use the alias; Task 9 checks the diff after the first run.
